# Google 로그인 대신 테스트 계정으로 로그인한다

- 상태: 확정 (2026-11-13). 방식은 2026-11-18에 확정했다. 아직 구현하지 않았다
- 관련: [scope.md](./scope.md), [project-positioning.md](./project-positioning.md), [data-model.md](./data-model.md)

## 결정

원본 서비스는 Firebase Auth의 Google 로그인을 쓴다. 이 프로젝트는 그것을 옮기지 않고 **미리 만들어 둔 테스트 계정으로 로그인**한다.

## 이유

- 보고서를 쓸 수 있을 정도면 된다. 인증은 이 과제의 주제가 아니다.
- Google OAuth 설정과 Firebase Auth 의존을 통째로 뺄 수 있다.

## 영향

- 사용자 등급(학생, 관리자, 마스터)은 데이터 모델에 그대로 둔다. 원본의 권한 구분이 등급에 달려 있기 때문이다.

| 등급 | 원본에서 할 수 있는 것 |
|---|---|
| 학생 | 공개 문서 읽기, 본인 예약·신청 읽기와 변경 |
| 관리자 | 관리자 앱 조회와 명단 내보내기 |
| 마스터 | 관리자 앱의 모든 작업 |

- 등급은 어느 서버에 로그인할 수 있는지와 어느 DB 계정으로 접속하는지도 정한다. 학생은 학생용 서버에, 관리자와 마스터는 관리자용 서버에 로그인한다([admin-server-split.md](./admin-server-split.md), [db-privileges.md](./db-privileges.md)).
- 실제 로그인이 없으므로 보고서의 한계로 적는다.

## 방식 (확정, 2026-11-18)

**로그인 화면에서 시드 계정 하나를 고른다. 비밀번호는 없다.**

1. 로그인 화면이 서버에서 계정 목록을 받아 보여 준다.
2. 하나를 고르면 그 계정의 이메일을 `POST /api/auth/login`에 보낸다.
3. 서버는 `users`에서 그 이메일을 찾고, 등급이 그 서버에 맞으면 세션을 만든다. 세션에는 사용자 ID와 등급이 들어간다.
4. 이후 요청은 세션 쿠키로 식별한다. 세션이 없는 요청은 401이다.

- 세션은 서버 메모리에 둔다. 서버를 다시 띄우면 로그인이 풀린다.
- Spring Security는 쓰지 않는다. 인증은 이 과제의 주제가 아니고, 필요한 것은 "지금 누구인가"뿐이다.
- 계정은 시드 데이터에 있다: 학생 5, 관리자 1, 마스터 1([`db/init/04-seed.sql`](../../db/init/04-seed.sql)).

검토한 대안은 이메일과 공용 비밀번호를 입력하는 것이었다. 비밀번호가 공개 저장소에 적혀 있어서 더해지는 것이 없고 입력 단계만 는다.

## 서버가 등급을 검사하는 곳

| 경계 | 검사하는 곳 |
|---|---|
| 어느 서버에 로그인할 수 있나 | 서버 코드. 학생용 서버는 학생만, 관리자용 서버는 관리자와 마스터만 로그인시킨다 |
| 로그인한 뒤 무엇을 할 수 있나 (역할 간) | DB 권한. 관리자용 서버는 등급에 맞는 DB 계정으로 접속할 뿐이고 쓰기 앞에서 등급을 검사하지 않는다([admin-server-split.md](./admin-server-split.md)) |
| 누구의 데이터인가 (사용자 간) | 서버 코드. 세션의 사용자 ID로 쿼리를 거른다([db-privileges.md](./db-privileges.md)) |

## 한계

누구나 아무 계정으로 로그인할 수 있다. 로컬에서만 실행하는 과제용 구현이라 받아들인다([local-only.md](./local-only.md)). 보고서의 한계에 적는다.
