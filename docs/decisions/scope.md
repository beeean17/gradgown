# 학위복 대여와 St:talk 두 서비스를 모두 구현한다

- 상태: 확정 (2026-11-13). 관리자 기능의 범위와 테스터 권한은 2026-11-18에 확정했다
- 관련: [topic.md](./topic.md), [project-positioning.md](./project-positioning.md), [data-model.md](./data-model.md)

## 결정

grad42가 운영하는 **두 서비스를 모두** 옮긴다. 하나만 고르지 않는다.

| 서비스 | 내용 |
|---|---|
| 학위복 대여 | 회차마다 시간대(슬롯)를 열고, 학생이 대여·반납 시각과 사이즈를 골라 예약한다 |
| St:talk | 졸업생 초청 멘토링 행사. 학생이 1차시·2차시에 들을 멘토를 하나씩 골라 신청한다 |

## 포함하는 기능

| 영역 | 기능 |
|---|---|
| 학위복 대여 (학생) | 예약 신청, 변경, 취소, 내 예약 조회 |
| St:talk (학생) | 신청, 변경, 취소, 내 신청 조회 |
| 관리자 | 회차별 예약 명단 검색, 행사별 신청 명단 검색, 선택지 × 차시 신청 인원 집계, 공지·FAQ·감사 로그 조회 |
| 마스터 | 회차와 행사의 접수 열기·닫기 |
| 공통 | 공지 읽기, 작업 감사 로그 기록 |

FAQ는 학생 웹에 화면이 없다. 원본에서 공지로 합쳐졌고 관리자 앱만 다룬다([contracts/web-api.md](../contracts/web-api.md)). FAQ 테이블은 관리자 조회용으로만 둔다.

두 서비스 모두 정원, 대기 순번, 선착순 마감이 없다. 원본 서비스도 마찬가지다.

## 제외하는 것

| 항목 | 이유 |
|---|---|
| 메일 발송 | 원본에서도 보류 상태다 |
| 필드 암호화, 속도 제한, 봇 차단 | 과제용이다([project-positioning.md](./project-positioning.md)) |
| 기존 Firestore 데이터 이관 | 시드 데이터로 시작한다 |
| 수령·반납 완료(`completed`), 참석(`attended`) 처리 | 원본에서도 아무 화면이 쓰지 않는다 |
| Google 로그인 | [test-login.md](./test-login.md) |
| 관리자의 나머지 쓰기: 회차·행사 설정 저장, 공지·FAQ 작성, 예약·신청 수정과 영구 삭제, 관리자 등록 | 쓰기는 접수 열기·닫기 하나로 충분하다(아래 "관리자 쓰기") |
| 명단 내보내기(xlsx, csv) | DB와 무관한 파일 생성 기능이다 |
| 테스터 권한 | 아래 "테스터 권한" |

## 관리자 쓰기 (확정, 2026-11-18)

관리자 쪽의 쓰기는 **마스터가 회차와 행사의 접수(`is_open`)를 켜고 끄는 것 하나만** 넣는다.

- 쓰기가 하나는 있어야 "관리자는 거부되고 마스터는 된다"를 앱에서 보일 수 있다. 하나도 없으면 마스터 DB 계정은 앱에서 쓰이지 않는다([admin-server-split.md](./admin-server-split.md)).
- 브라우저 테스트의 "접수를 닫으면 신청 버튼이 사라진다" 시나리오를 DB에 직접 손대지 않고 할 수 있다([동적 계열](../testing/dynamic.md)).
- St:talk의 접수를 열려면 선택지 7개 모두 이름이 있어야 한다는 규칙(MNT-51)은 이 기능에 적용된다.

회차·행사의 나머지 설정, 공지·FAQ, 예약·신청의 수정과 영구 삭제는 넣지 않는다. 그 데이터는 시드 데이터로만 들어간다.

## 테스터 권한 (확정, 2026-11-18)

**넣지 않는다.** 원본에는 접수 기간 밖에서도 신청할 수 있는 테스터 목록(`settings_private/*_testing`)이 있다. 운영자가 접수 전에 점검하려고 쓰는 기능이라, 운영하지 않는 이 프로젝트에는 쓸 사람이 없다. 테이블은 11개 그대로다.

- 기간 판정(RES-21, MNT-21)에서 테스터 예외가 빠진다. 원본과 달라지는 점이므로 보고서에 제외한 것으로 적는다.
- 가져온 웹의 테스터 판정은 항상 거짓이다([API 계약](../contracts/web-api.md)).

## 영향

- 두 서비스를 다 구현해도 보고서 6쪽에는 전부 담을 수 없다. 공통 구조를 설명하고, 기능 흐름은 한 서비스만 골라 자세히 쓴다. 예시 보고서(항공 예약)도 기능 영역 두 개만 골라 설명했다.
- 두 서비스가 같은 뼈대(회차 → 선택 단위 → 신청)를 가지므로 데이터 모델에서 그 대칭을 살린다([data-model.md](./data-model.md)).
