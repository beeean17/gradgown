# 평가는 DB 수준 비교를 중심으로 한다

- 상태: 방향은 제안 (2026-11-13). 측정할 항목, 데이터 규모, Firebase 쪽 수치를 얻는 방법은 2026-11-19에 확정하고 측정했다
- 관련: [topic.md](./topic.md), [local-only.md](./local-only.md), [data-model.md](./data-model.md), [db-privileges.md](./db-privileges.md), [과제 요구사항](../requirements/course-requirements.md)

## 제안

보고서의 Evaluation은 **"MySQL이 Firestore보다 빠르다"가 아니라, 구조가 바뀌어서 무엇이 달라졌는지**를 보인다. 중심은 DB 수준의 비교이고, 프론트 로딩 수치는 배경으로만 쓴다.

## 이유

- 주제의 동기 중 하나가 성능 개선이다([topic.md](./topic.md)). 보고서 양식도 결과와 그 이유를 쓰라고 요구한다.
- Firestore의 단일 문서 읽기는 그 자체로 느리지 않다. 엔진끼리의 속도 비교는 근거를 대기 어렵다.
- localhost에서만 실행하므로([local-only.md](./local-only.md)) 운영 중인 Firebase 사이트와 같은 조건으로 응답 시간을 잴 수 없다.
- 데이터베이스 과목의 보고서다.

## 평가 항목 후보

### 1. 조회 구조

grad42 `feat/spring-migration` 브랜치의 `docs/migration/04-api.md`가 현행 관리자 API의 비효율을 A1~A8로 정리해 두었다. 그중 DB 구조에서 오는 것이 후보다.

| 항목 | Firebase 버전 | MySQL 버전에서 보일 것 |
|---|---|---|
| A1 예약 명단 검색 | 예약 51건을 읽어 50건을 보여 주고, 이름·학번·전화·상태 필터를 그 페이지 안에서만 적용한다 | `WHERE`, 인덱스, 페이지네이션. 첫 페이지 밖의 일치 항목도 찾는다 |
| A4 공지·FAQ | 각각 문서 하나의 map이다. 숨김 항목도 공개로 읽히고, 저장할 때 문서 전체를 다시 쓴다 | 행 단위 조회와 갱신. 노출 조건을 `WHERE`로 적용한다 |
| A5 감사 로그 | 최근 200건을 읽어 브라우저에서 검색한다 | 서버 필터와 페이지네이션 |
| St:talk 신청 현황 | 행사의 신청을 모두 읽어 브라우저에서 선택지 × 차시 인원을 센다 | `GROUP BY` 한 번 |

잴 수 있는 지표는 읽는 문서 수 대 반환 행 수, 요청 왕복 횟수, 응답 크기, `EXPLAIN` 실행 계획이다.

### 2. 정합성

규칙을 코드가 아니라 스키마가 보장한다는 것을 보인다([data-model.md](./data-model.md) "코드에서 DB 제약으로 옮기는 규칙").

- 같은 회차에 두 번째 예약을 넣으면 UNIQUE 위반으로 거부되는 것
- 두 차시에 같은 선택지를 넣으면 `CHECK` 위반으로 거부되는 것
- 같은 `operation_id`로 두 번 요청하면 한 번만 처리되는 것
- 동시에 같은 예약을 고치면 한쪽이 `version` 충돌로 거부되는 것

### 3. 접근 제어

등급 간 경계를 DB가 지킨다는 것을 보인다([db-privileges.md](./db-privileges.md)).

- 학생 계정으로 예약을 `DELETE`하면 권한 오류로 거부되는 것
- 학생 계정으로 회차 설정을 `UPDATE`하면 거부되는 것
- 학생 계정으로 공지 뷰를 읽으면 숨김 공지가 나오지 않는 것
- 관리자 계정으로 어떤 테이블이든 쓰면 거부되는 것

### 4. 프론트 로딩 (배경)

grad42 `docs/perf/2026-11-04-baseline.md`의 운영 측정값을 Background에서 인용한다.

- 모바일 Lighthouse 기준 홈 LCP는 10.85초였고, 프론트 개선 후 8.68초다.
- 첫 화면 내용이 "JS 1.4MB 실행 → reCAPTCHA 로드 → App Check 토큰 → Firestore 응답"을 차례로 기다린다.
- Firestore SDK가 번들의 24.9%, reCAPTCHA가 356KB다.

이전하면 Firestore SDK와 App Check가 빠지고 REST 호출로 바뀐다. 다만 로컬 실행으로는 이 효과의 절대값을 운영과 비교할 수 없다. 번들 크기와 첫 화면 요청 수처럼 실행 환경과 무관한 것만 전후로 비교한다.

## 한계로 적을 것

보고서 양식은 단점과 안정성도 쓰라고 요구한다.

- Firestore의 실시간 구독(`onSnapshot`)이 없어진다. 관리자가 접수를 닫아도 열려 있는 화면에 바로 반영되지 않는다. 학생 웹은 30초마다 다시 읽는 것으로 대신했다(2026-11-18). 서버가 변경을 밀어 주는 것이 아니라 웹이 물어보는 것이고, 요청 수가 그만큼 는다.
- Firebase가 대신 해 주던 인증, 보안 규칙, 호스팅을 직접 맡아야 한다. 이 프로젝트는 그 부분을 테스트 로그인과 로컬 실행으로 생략했다.
- Firestore Security Rules는 사용자 단위로 읽기를 막아 주었다. MySQL 권한은 계정 단위라 "본인 예약만 본다"는 서버 코드가 지켜야 한다([db-privileges.md](./db-privileges.md)).
- 측정은 로컬 환경의 합성 데이터로 한다.

## 측정 방법 (확정, 2026-11-19)

| 정한 것 | 내용 |
|---|---|
| 측정 항목 | 조회 구조 넷(예약 명단 검색 A1, St:talk 신청 인원 집계, 감사 로그 A5, 공지 A4)과 프론트 번들·첫 화면 요청 |
| 데이터 규모 | 실제에 가까운 규모(회차의 예약 1,000건, 행사의 신청 300건, 감사 로그 5,000건, 공지 30건)와 그 100배. 실제 규모는 추정이다 |
| Firebase 쪽 수치 | **로컬 Firestore 에뮬레이터**에 같은 데이터를 넣고 원본의 쿼리를 실행해서 잰다. 운영 중인 Firebase에는 어떤 요청도 보내지 않는다 |

측정 도구는 `eval` 모듈이고, 방법과 표를 읽는 법은 [eval/README.md](../../eval/README.md)에 있다. 정합성(2번)과 접근 제어(3번)는 측정이 아니라 테스트로 보였다([동적 계열](../testing/dynamic.md)).

## 측정 결과 (2026-11-19)

전체 표와 실행 계획은 [`eval/results/actual.md`](../../eval/results/actual.md), [`eval/results/x100.md`](../../eval/results/x100.md), [`eval/results/bundle.md`](../../eval/results/bundle.md)에 있다. 아래는 요약이다. "읽은 것"은 Firestore는 문서 수, MySQL은 스토리지 엔진이 읽은 행 수다.

| 질문 | 규모 | Firestore (원본의 쿼리) | MySQL (이 프로젝트의 SQL) |
|---|---|---|---|
| 회차에서 한 사람 찾기 | 예약 1,000건 | 첫 페이지에서는 못 찾는다. 10번 요청해 510문서(513 KB)를 읽고서야 찾는다 | 요청 1번, 1행(470 B). 1,004행을 읽는다 |
| | 예약 100,000건 | 1,000번 요청, 51,000문서(50.2 MB) | 요청 1번, 1행. 100,004행을 읽는다(67 ms) |
| St:talk 신청 인원 집계 | 신청 300건 | 300문서(236 KB)를 받아 브라우저에서 센다. 맞다 | 요청 1번, 8행(457 B). 맞다 |
| | 신청 30,000건 | 1,001문서(790 KB). **틀린다.** 1,000건까지만 읽어 27,000명을 900명으로 센다 | 요청 1번, 8행. 맞다(37 ms) |
| 감사 로그에서 거부된 요청 보기 | 5,000건 | 최신 200문서(274 KB). 그 밖의 기록은 못 찾는다 | 51행(17 KB). 인덱스가 없으면 5,054행, 있으면 303행을 읽는다 |
| | 500,000건 | 같다. 200문서 | 인덱스가 없으면 500,054행(103 ms), 있으면 303행(0.8 ms) |
| 학생에게 내려가는 공지 | 30건(숨김 5) | 문서 하나(34 KB)에 숨김 5건이 함께 내려온다 | 노출 중인 25행(22 KB). 숨김은 내려오지 않는다 |
| 예약 명단의 첫 페이지 | 두 규모 모두 | 51문서 | 51행. 규모와 무관하게 190행 안팎을 읽는다 |

프론트는 학생 웹의 전체 JS가 1,444 KB에서 890 KB로(38% 감소), 첫 화면 JS가 1,155 KB에서 598 KB로(48% 감소) 줄었다. 첫 화면이 다른 도메인(reCAPTCHA, Firebase Auth)에 보내던 요청이 없어졌다.

### 결과에서 읽을 수 있는 것

- **차이는 속도가 아니라 "어디서 거르느냐"에서 나온다.** 원본은 페이지 하나를 통째로 받아 브라우저에서 거른다. 그래서 찾는 것이 그 페이지 밖에 있으면 틀린 답("결과 없음")을 보이거나, 사람이 페이지를 넘겨 가며 전부 내려받아야 한다. MySQL은 `WHERE`가 전체에 적용된 뒤 답만 내려온다.
- **원본의 상한은 조용히 틀린다.** 신청 현황은 1,000건, 감사 로그는 200건까지만 읽는다. 지금 규모(신청 수백 건)에서는 문제가 없고, 넘는 순간 화면은 오류 없이 틀린 숫자를 보인다. 실제 규모에서는 두 쪽 모두 맞는 답을 냈다는 점도 함께 적어야 한다.
- **MySQL이 적게 읽는 것은 아니다.** 이름 검색은 `LIKE '%…%'`라서 회차의 예약을 모두 읽는다(100,000건에서 67 ms). 인덱스가 도울 수 없는 조건이다. 집계도 신청 전부를 두 번 읽는다. 줄어든 것은 읽는 양이 아니라 네트워크로 내려오는 양과 왕복 횟수다.
- **인덱스가 필요한 곳은 측정이 알려 주었다.** 감사 로그 목록은 최신순으로 한 페이지씩 읽는데, 보조 인덱스가 없으면 페이지마다 테이블 전체를 정렬했다. `(created_at, operation_id)` 인덱스를 더하니 읽는 행이 500,054에서 303으로 줄었다. 이 인덱스를 스키마에 넣었다([data-model.md](./data-model.md)). 예약 명단의 첫 페이지는 FK가 만든 인덱스로 이미 충분했다.
- **숨김 공지는 크기의 문제가 아니라 노출의 문제다.** 원본에서는 숨긴 공지의 제목과 본문이 누구에게나 내려간다. 학생 DB 계정은 뷰만 읽으므로 서버 코드가 틀려도 내려갈 수 없다.

### 이 측정의 한계

- 에뮬레이터는 실제 Firestore가 아니다. 그래서 시간은 비교하지 않았다. MySQL의 시간도 개발 머신의 컨테이너에서 잰 참고값이다.
- 원본의 쿼리는 원본 코드를 읽고 같은 모양으로 다시 쓴 것이다. 원본 앱을 그대로 돌린 것이 아니다.
- 응답 크기는 어림값이다. Firestore는 REST 응답에서 들여쓰기를 뺀 크기이고, MySQL은 결과 행을 JSON으로 쓴 크기다.
- "한 사람 찾기"는 찾는 사람이 회차의 한가운데에 있다고 두었다. 최근에 예약한 사람이면 원본도 첫 페이지에서 찾는다.
- 실제 규모는 추정이다. 원본 문서에는 St:talk이 "수백 건 규모"라는 말만 있다.
- 원본의 첫 화면 요청 수는 직접 재지 않고 grad42의 운영 기록을 옮겼다. 원본 웹을 띄우면 운영 Firebase에 닿기 때문이다.
