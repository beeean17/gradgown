# 평가는 DB 수준 비교를 중심으로 한다

- 상태: 방향은 제안 (2026-11-13). 측정할 항목, 데이터 규모, Firebase 쪽 수치를 얻는 방법은 2026-11-19에 확정하고 측정했다
- 관련: [topic.md](./topic.md), [local-only.md](./local-only.md), [data-model.md](./data-model.md), [db-privileges.md](./db-privileges.md), [과제 요구사항](../requirements/course-requirements.md)

## 제안

보고서의 Evaluation은 **"MySQL이 Firestore보다 빠르다"가 아니라, 구조가 바뀌어서 무엇이 달라졌는지**를 보인다. 중심은 DB 수준의 비교이고, 프론트 로딩 수치는 배경으로만 쓴다.

## 이유

- 주제의 동기 중 하나가 성능 개선이다([topic.md](./topic.md)). 보고서 양식도 결과와 그 이유를 쓰라고 요구한다.
- Firestore의 단일 문서 읽기는 그 자체로 느리지 않다. 엔진끼리의 속도 비교는 근거를 대기 어렵다.
- localhost에서만 실행하므로([local-only.md](./local-only.md)) 운영 중인 Firebase 사이트와 같은 조건으로 응답 시간을 잴 수 없다.
- 데이터베이스 과목의 보고서다.

## 평가 항목 후보

### 1. 조회 구조

grad42 `feat/spring-migration` 브랜치의 `docs/migration/04-api.md`가 현행 관리자 API의 비효율을 A1~A8로 정리해 두었다. 그중 DB 구조에서 오는 것이 후보다.

| 항목 | Firebase 버전 | MySQL 버전에서 보일 것 |
|---|---|---|
| A1 예약 명단 검색 | 예약 51건을 읽어 50건을 보여 주고, 이름·학번·전화·상태 필터를 그 페이지 안에서만 적용한다 | `WHERE`, 인덱스, 페이지네이션. 첫 페이지 밖의 일치 항목도 찾는다 |
| A4 공지·FAQ | 각각 문서 하나의 map이다. 숨김 항목도 공개로 읽히고, 저장할 때 문서 전체를 다시 쓴다 | 행 단위 조회와 갱신. 노출 조건을 `WHERE`로 적용한다 |
| A5 감사 로그 | 최근 200건을 읽어 브라우저에서 검색한다 | 서버 필터와 페이지네이션 |
| St:talk 신청 현황 | 행사의 신청을 모두 읽어 브라우저에서 선택지 × 차시 인원을 센다 | `GROUP BY` 한 번 |

잴 수 있는 지표는 읽는 문서 수 대 반환 행 수, 요청 왕복 횟수, 응답 크기, `EXPLAIN` 실행 계획이다.

### 2. 정합성

규칙을 코드가 아니라 스키마가 보장한다는 것을 보인다([data-model.md](./data-model.md) "코드에서 DB 제약으로 옮기는 규칙").

- 같은 회차에 두 번째 예약을 넣으면 UNIQUE 위반으로 거부되는 것
- 두 차시에 같은 선택지를 넣으면 `CHECK` 위반으로 거부되는 것
- 같은 `operation_id`로 두 번 요청하면 한 번만 처리되는 것
- 동시에 같은 예약을 고치면 한쪽이 `version` 충돌로 거부되는 것

### 3. 접근 제어

등급 간 경계를 DB가 지킨다는 것을 보인다([db-privileges.md](./db-privileges.md)).

- 학생 계정으로 예약을 `DELETE`하면 권한 오류로 거부되는 것
- 학생 계정으로 회차 설정을 `UPDATE`하면 거부되는 것
- 학생 계정으로 공지 뷰를 읽으면 숨김 공지가 나오지 않는 것
- 관리자 계정으로 어떤 테이블이든 쓰면 거부되는 것

### 4. 프론트 로딩 (배경)

grad42 `docs/perf/2026-11-04-baseline.md`의 운영 측정값을 Background에서 인용한다.

- 모바일 Lighthouse 기준 홈 LCP는 10.85초였고, 프론트 개선 후 8.68초다.
- 첫 화면 내용이 "JS 1.4MB 실행 → reCAPTCHA 로드 → App Check 토큰 → Firestore 응답"을 차례로 기다린다.
- Firestore SDK가 번들의 24.9%, reCAPTCHA가 356KB다.

이전하면 Firestore SDK와 App Check가 빠지고 REST 호출로 바뀐다. 다만 로컬 실행으로는 이 효과의 절대값을 운영과 비교할 수 없다. 번들 크기와 첫 화면 요청 수처럼 실행 환경과 무관한 것만 전후로 비교한다.

## 한계로 적을 것

보고서 양식은 단점과 안정성도 쓰라고 요구한다.

- Firestore의 실시간 구독(`onSnapshot`)이 없어진다. 관리자가 접수를 닫아도 열려 있는 화면에 바로 반영되지 않는다. 학생 웹은 30초마다 다시 읽는 것으로 대신했다(2026-11-18). 서버가 변경을 밀어 주는 것이 아니라 웹이 물어보는 것이고, 요청 수가 그만큼 는다.
- Firebase가 대신 해 주던 인증, 보안 규칙, 호스팅을 직접 맡아야 한다. 이 프로젝트는 그 부분을 테스트 로그인과 로컬 실행으로 생략했다.
- Firestore Security Rules는 사용자 단위로 읽기를 막아 주었다. MySQL 권한은 계정 단위라 "본인 예약만 본다"는 서버 코드가 지켜야 한다([db-privileges.md](./db-privileges.md)).
- 측정은 로컬 환경의 합성 데이터로 한다.

## 측정 방법 (확정, 2026-11-19)

| 정한 것 | 내용 |
|---|---|
| 측정 항목 | 조회 구조 넷(예약 명단 검색 A1, St:talk 신청 인원 집계, 감사 로그 A5, 공지 A4)과 프론트 번들·첫 화면 요청 |
| 데이터 규모 | 실제에 가까운 규모(회차의 예약 1,000건, 행사의 신청 300건, 감사 로그 5,000건, 공지 30건)와 그 100배. 실제 규모는 추정이다 |
| Firebase 쪽 수치 | **로컬 Firestore 에뮬레이터**에 같은 데이터를 넣고 원본의 쿼리를 실행해서 잰다. 운영 중인 Firebase에는 어떤 요청도 보내지 않는다 |

측정 도구는 `eval` 모듈이고, 방법과 표를 읽는 법은 [eval/README.md](../../eval/README.md)에 있다. 정합성(2번)과 접근 제어(3번)는 측정이 아니라 테스트로 보였다([동적 계열](../testing/dynamic.md)).

## 측정 결과 (2026-11-19)

전체 표와 실행 계획은 [`eval/results/actual.md`](../../eval/results/actual.md), [`eval/results/x100.md`](../../eval/results/x100.md), [`eval/results/bundle.md`](../../eval/results/bundle.md)에 있다. 아래는 요약이다. "읽은 것"은 Firestore는 쿼리가 돌려준 문서 수, MySQL은 스토리지 엔진이 읽은 행 수다. 크기는 어림값이다.

| 질문 | 규모 | Firestore 에뮬레이터 (원본의 쿼리) | MySQL (이 프로젝트의 SQL) |
|---|---|---|---|
| 회차에서 한 사람 찾기 | 예약 1,000건 | 첫 페이지(51문서)에는 없다. 다음 페이지를 눌러 10번 요청, 510문서(513 KB)를 받고서야 찾는다 | SQL 1번, 1행(470 B). 1,004행을 읽는다 |
| | 예약 100,000건 | 1,000번 요청, 51,000문서(50.2 MB) | SQL 1번, 1행. 100,004행을 읽는다(67 ms) |
| St:talk 신청 인원 집계 | 신청 300건 | 300문서(236 KB)를 받아 브라우저에서 센다. 맞다 | SQL 1번, 8행(457 B). 맞다 |
| | 신청 30,000건 | 1,001문서(790 KB)를 읽고 **오류를 보인다.** 1,000건을 넘으면 읽기를 거부한다. 집계도 명단도 볼 수 없다 | SQL 1번, 8행. 맞다. 168,012행을 읽는다(38 ms) |
| 감사 로그에서 오래된 거부 요청 찾기 | 5,000건 | 최신 200문서(274 KB) 안에 없다. 그 밖은 이 화면에서 볼 수 없다 | 요청 ID로 찾으면 SQL 1번, 2행을 읽는다. 거부 건만 걸러 넘기면 10페이지, 모두 1,028행 |

| 학생에게 내려가는 공지 | 30건(숨김 5) | 문서 하나(34 KB)에 숨김 5건이 함께 내려온다 | 노출 중인 25행(22 KB). 숨김은 내려오지 않는다 |
| 예약 명단의 첫 페이지 | 두 규모 모두 | 51문서(51 KB) | 51행(23 KB). 규모와 무관하게 190행 안팎을 읽는다 |

감사 로그의 첫 페이지(거부 건 51행)를 읽는 데 든 행 수는 인덱스에 따라 달랐다.

| 감사 로그 500,000건에서 | 보조 인덱스 없음 | `(created_at, operation_id)` | `(outcome, created_at, operation_id)` 추가 |
|---|---|---|---|
| 거부 건(전체의 20%)의 첫 페이지 | 500,054행 (103 ms) | 303행 (0.7 ms) | 102행 (0.7 ms) |
| 한 건도 없는 결과(`failed`)의 첫 페이지 | — | 500,002행 (389 ms) | 1행 (0.3 ms) |

프론트는 학생 웹의 전체 JS가 1,444 KB에서 890 KB로(38% 감소), 첫 화면 JS가 1,155 KB에서 598 KB로(48% 감소) 줄었다. 첫 화면이 reCAPTCHA Enterprise(App Check)와 Firestore에 보내던 요청이 없어지고, 같은 출처로 가는 REST 요청 넷이 됐다.

### 결과에서 읽을 수 있는 것

- **차이는 속도가 아니라 "어디서 거르느냐"에서 나온다.** 원본은 페이지 하나를 통째로 받아 브라우저에서 거른다. 그래서 찾는 사람이 그 페이지 밖에 있으면 찾을 수 없고, 화면도 "현재 페이지 검색"이라고 그렇게 밝힌다. 찾으려면 사람이 페이지를 넘겨 가며 전부 내려받아야 한다. MySQL은 `WHERE`가 회차 전체에 적용된 뒤 답만 내려온다. 이것을 보이는 것은 "한 사람 찾기"다.
- **원본의 상한은 숨겨져 있지 않다.** 신청 현황은 1,000건을 넘으면 오류를 내고, 감사 로그 화면은 "최근 200건 안에서 검색"이라고 적는다. 틀린 숫자를 보이지는 않는다. 다만 그 설계로는 상한 밖을 다룰 수 없다. 이 서비스의 실제 규모(신청 수백 건)에서는 두 쪽 모두 맞는 답을 냈다는 점도 함께 적어야 한다.
- **MySQL이 적게 읽는 것은 아니다.** 이름 검색은 `LIKE '%…%'`라서 회차의 예약을 모두 읽는다(100,000건에서 67 ms). 인덱스가 도울 수 없는 조건이다. 집계도 신청 전부를 두 번 읽는다. 한 사람 찾기에서 줄어든 것은 읽는 양이 아니라 네트워크로 내려오는 양과 왕복 횟수다.
- **집계 하나만 보면 8행이지만, 화면 전체는 아니다.** 관리자 앱의 신청 현황 화면은 집계와 함께 명단 전체도 받는다. 화면 하나로 보면 원본처럼 행사의 신청을 모두 내려받고, 요청은 하나 더 많다. 표의 "SQL 1번, 8행"은 집계 질문에 든 것이다.
- **인덱스가 필요한 곳과 필요한 모양은 측정이 알려 주었다.** 감사 로그 목록은 최신순으로 한 페이지씩 읽는데, 보조 인덱스가 없으면 페이지마다 테이블 전체를 정렬했다. `(created_at, operation_id)`를 더하니 303행으로 줄었지만, 드문 결과로 거르면 일치하는 행을 찾느라 그 인덱스 전체를 읽었다. `(outcome, created_at, operation_id)`를 더해야 1행이 됐다. 두 인덱스를 스키마에 넣었다([data-model.md](./data-model.md)). 예약 명단의 첫 페이지는 FK가 만든 인덱스로 이미 충분했다.
- **페이지를 넘기는 조건을 어떻게 쓰느냐가 실행 계획을 바꿨다.** 처음에는 커서를 행 비교 `(created_at, operation_id) < (?, ?)`로 썼다. 뜻은 맞지만 MySQL은 이것을 인덱스 범위로 바꾸지 않아서, 페이지마다 가장 새 행부터 다시 훑었다(10번째 페이지가 열 페이지 분량을 읽었다). "더 이르거나, 같은 시각이면 ID가 더 작다"로 풀어 쓰니 페이지마다 읽는 양이 일정해졌다(시각 인덱스만으로 1,000페이지에 306,995행, 페이지당 약 300행). 측정을 검증하다가 드러난 것이다.
- **오래된 기록 하나를 찾는 방법은 넘기는 것이 아니라 키다.** 거부 건만 걸러서 넘기면 찾는 건까지 10페이지(500,000건에서는 1,000페이지)가 든다. 원본이 한 사람을 찾으려고 페이지를 넘기는 것과 같은 일이다. 요청 ID는 PK라서 한 번에 찾는다. 이전하면서 감사 로그 화면의 검색을 빼먹었다가, 이 측정을 검증하면서 요청 ID 검색으로 되살렸다.
- **숨김 공지는 크기의 문제가 아니라 노출의 문제다.** 원본에서는 숨긴 공지의 제목과 본문이 누구에게나 내려간다. 학생 DB 계정은 뷰만 읽으므로 서버 코드가 틀려도 내려갈 수 없다(이것은 이 측정이 아니라 권한 테스트가 보인다).

### 이 측정의 한계

- 에뮬레이터는 실제 Firestore가 아니다. 그래서 시간은 비교하지 않았다. MySQL의 시간도 개발 머신의 컨테이너에서 잰 참고값이다.
- 원본의 쿼리는 원본 코드를 읽고 같은 모양으로 다시 쓴 것이다. 원본 앱을 그대로 돌린 것이 아니다.
- 응답 크기는 어림값이고, 차이에는 원인이 섞여 있다. Firestore는 REST 응답에서 들여쓰기를 뺀 크기이고 MySQL은 결과 행을 JSON으로 쓴 크기다. 감사 로그는 200문서와 51행을 견주는 것이라 페이지 크기부터 다르고, 문서의 필드가 행의 컬럼보다 많다.
- "한 사람 찾기"는 찾는 사람이 회차의 한가운데에 있다고 두었다. 최근에 예약한 사람이면 원본도 첫 페이지에서 찾는다. 원본에는 명단 전체를 xlsx로 내려받는 길도 있었다(모든 페이지를 차례로 읽는다).
- 원본의 페이지 안 검색은 학과도 본다. 이 프로젝트의 검색은 이름·학번·전화만 본다.
- 원본에는 Cloud Logging에서 요청 ID로 찾는 "서버 로그" 화면이 따로 있었다. "200건 밖은 볼 수 없다"는 감사 로그 화면에 한한 말이다.
- 100배 규모는 이 서비스가 겪을 규모가 아니다. 건수에 따른 변화와 인덱스의 효과를 보려고 둔 것이다. 실제 규모도 추정이다. 원본 문서에는 St:talk이 "수백 건 규모"라는 말만 있다.
- 합성 데이터는 고르게 퍼져 있다. 거부 건이 정확히 다섯에 하나라서 303행 같은 값이 일정하게 나온다. 실제 분포에서는 걸러지는 비율에 따라 달라진다.
- MySQL 쪽의 "요청"은 서버가 DB에 보낸 SQL 문장이다. 브라우저가 서버에 보낸 요청이나 화면 하나가 여는 요청 전체가 아니다.
- 원본의 첫 화면 요청 수는 직접 재지 않고 grad42의 기록을 옮겼다. 원본 웹을 띄우면 운영 Firebase에 닿기 때문이다. 그 기록의 값은 가져온 버전과 조건이 같지 않다([`eval/results/bundle.md`](../../eval/results/bundle.md)).

### 이 측정을 검증한 일

측정과 위의 해석을 쓴 뒤, 쓰지 않은 쪽(AI 에이전트)에게 원본 코드와 대조해 검증하게 했다. 숫자는 맞게 옮겨져 있었지만 주장 셋이 틀리거나 지나쳤고, 고쳐서 다시 쟀다.

| 처음 쓴 것 | 실제 |
|---|---|
| 원본은 신청이 1,000건을 넘으면 27,000명을 900명으로 "조용히 틀리게" 센다 | 원본은 그때 오류를 내고 집계를 보이지 않는다. 원본 코드의 `throw` 한 줄을 놓쳤다 |
| 이전으로 Firebase Auth와 Google Fonts로 가던 요청이 없어졌다 | 그것들은 grad42가 가져온 버전 이전에 스스로 없앤 것이었다. 옛 버전의 기록을 옮겨 적었다 |
| 인덱스를 더하면 감사 로그는 "테이블이 얼마나 크든" 한 페이지에 303행을 읽는다 | 첫 페이지에서, 거부 비율이 20%일 때만 그랬다. 뒤 페이지는 커서 조건 때문에 처음부터 다시 훑었고, 드문 결과는 인덱스 전체를 읽었다 |

셋 다 **유리한 쪽으로 틀렸다.** 비교를 직접 설계한 쪽이 결과를 해석하면 그렇게 기운다는 것을 보여 준다.
