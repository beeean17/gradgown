# MySQL은 Docker 컨테이너로 띄운다

- 상태: 확정 (2026-11-14). 이미지 버전과 스키마를 관리하는 방법은 2026-11-16에 확정했다. 나머지 구성은 제안이다. 개발용 컨테이너와 테스트용 컨테이너를 모두 띄워 확인했다(2026-11-16, MySQL 8.4.13)
- 관련: [local-only.md](./local-only.md), [ci.md](./ci.md), [db-privileges.md](./db-privileges.md), [동적 계열](../testing/dynamic.md)

## 결정

MySQL을 **Docker 컨테이너로** 띄운다. 개발, 테스트, CI에서 모두 같다. macOS에 MySQL을 직접 설치하지 않는다.

## "어떻게 띄울지"의 뜻

어디서 실행할지는 이미 정해져 있었다. 개발 중에는 개발 머신([local-only.md](./local-only.md)), CI에서는 GitHub의 실행 환경이다([ci.md](./ci.md)). 이 결정은 그 안에서 MySQL 프로세스를 어떤 방식으로 실행할지를 정한 것이다.

## 이유

- **CI와 같은 환경이다.** GitHub Actions도 MySQL을 컨테이너로 띄운다. 로컬과 CI가 같은 이미지, 같은 버전을 쓴다.
- **재현할 수 있다.** 명령 하나로 빈 DB에서 테이블, 계정 셋, `GRANT`, 시드 데이터까지 올라온다. 보고서가 요구하는 "읽은 사람이 재현할 수 있어야 한다"에 맞는다.
- **테스트용 DB를 분리하기 쉽다.** 테스트가 임시 컨테이너를 띄웠다가 지우면 개발용 데이터와 섞이지 않는다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| macOS에 직접 설치(Homebrew 등) | 버전과 설정이 개발 머신에만 있어 CI와 어긋날 수 있다. 계정 셋과 초기화를 손으로 해야 한다 |
| 슬라이드의 방법(소스 빌드, APT, Windows 설치 프로그램) | Linux와 Windows 기준이다. 재현성 면에서 직접 설치와 같은 문제가 있다 |

## 구성 (제안)

| 용도 | 방식 |
|---|---|
| 개발 | Compose 파일 하나로 MySQL을 띄운다. 처음 뜰 때 초기화 스크립트가 테이블, 뷰, 계정 셋, `GRANT`, 시드 데이터를 만든다 |
| 테스트 | 테스트가 임시 컨테이너를 직접 띄운다(Testcontainers). 개발용 DB와 따로다 |
| CI | 테스트와 같은 방식이다. GitHub의 Linux 실행 환경에 Docker가 들어 있다 |

서버와 웹은 컨테이너에 넣지 않고 개발 머신에서 직접 실행하는 것을 제안한다. 컨테이너에 넣으면 고칠 때마다 다시 빌드해야 한다.

## 이미지와 스키마 관리 (확정, 2026-11-16)

- **이미지는 `mysql:8.4`다.** 8.x의 장기 지원 버전이다. 개발(`compose.yaml`)과 테스트(`MySqlTestDatabase.IMAGE`)가 같은 태그를 쓰고, 둘이 어긋나면 `ComposeFileTest`가 실패한다.
- **스키마는 초기화 SQL 파일로만 관리한다. 마이그레이션 도구는 쓰지 않는다.** 운영 데이터가 없어서 변경 이력을 관리할 필요가 없고, 보고서에 SQL 파일을 그대로 실을 수 있다. 스키마를 바꾸면 파일을 고치고 컨테이너를 새로 만든다.

## 파일

| 파일 | 내용 |
|---|---|
| [`compose.yaml`](../../compose.yaml) | 개발용 MySQL. `127.0.0.1:3306`에만 연다 |
| [`db/conf/gradgown.cnf`](../../db/conf/gradgown.cnf) | 서버 설정. 시간대 `+09:00`, 문자 집합 `utf8mb4` |
| [`db/init/01-schema.sql`](../../db/init/01-schema.sql) | 테이블 11개([data-model.md](./data-model.md)) |
| [`db/init/02-views.sql`](../../db/init/02-views.sql) | 공지 뷰 |
| [`db/init/03-accounts.sql`](../../db/init/03-accounts.sql) | 계정 셋과 `GRANT`([db-privileges.md](./db-privileges.md)) |
| [`db/init/04-seed.sql`](../../db/init/04-seed.sql) | 시드 데이터. 만들어 낸 값뿐이다 |

이미지의 진입 스크립트는 데이터 디렉터리가 비어 있을 때만 `db/init`의 파일을 이름순으로 root 권한으로 실행한다. 테스트용 컨테이너도 같은 디렉터리를 같은 방식으로 실행하므로, 개발용 DB와 테스트용 DB는 같은 과정으로 만들어진다.

```sh
docker compose up -d --wait   # 띄운다. 처음 뜰 때 db/init이 실행된다
docker compose down -v        # 컨테이너와 데이터를 지운다. db/init을 고친 뒤에는 이렇게 지우고 다시 띄운다
```

시드 데이터의 날짜는 고정이다. 현재 회차와 현재 행사의 신청 기간은 2026-11-01부터 2027년 1월까지다. 그 뒤에 실행하면 접수가 기간 밖으로 보인다.

## 띄워 보고 알게 된 것 (2026-11-16)

- **초기화 스크립트는 설정 파일의 시간대로 실행되지 않는다.** 진입 스크립트가 초기화용 임시 서버를 `--default-time-zone=SYSTEM`으로 띄우기 때문이다. 컨테이너의 시스템 시간대는 UTC다. 시각을 넣는 SQL 파일(`04-seed.sql`)은 맨 위에서 `SET time_zone = '+09:00'`을 해야 한다. 자세한 경위는 [data-model.md](./data-model.md)의 "구현하면서 알게 된 것"에 있다.
- **컨테이너 안의 `mysql` 클라이언트는 기본 문자 집합이 `latin1`이다.** 한글이 `?`로 보인다. 저장된 값은 정상이었다. 설정 파일의 `[client]`에 `utf8mb4`를 넣어 고쳤다.
- **헬스체크는 TCP로 한다.** 초기화용 임시 서버는 소켓으로만 열리므로, TCP로 확인하면 초기화가 끝난 뒤에야 통과한다. `docker compose up -d --wait`가 돌아오면 시드 데이터까지 들어가 있다.

## 영향

- 개발과 테스트를 하려면 Docker Desktop이 켜져 있어야 한다.
- 초기화 스크립트가 스키마의 기준이 된다. DDL, `GRANT`, 시드 데이터가 저장소에 SQL 파일로 들어간다.
- 계정 셋의 비밀번호가 설정 파일에 들어간다. 테스트 전용 값만 쓴다([ci.md](./ci.md)).

## 미정

- 테스트 사이에 DB 상태를 되돌리는 방법([동적 계열](../testing/dynamic.md)). 1·2층은 테스트마다 트랜잭션을 되돌린다. 서버를 띄우는 층은 정하지 않았다.
- 개발용 DB의 데이터를 컨테이너를 지워도 남길지. 지금 `compose.yaml`은 이름 붙인 볼륨을 두지 않아서 `docker compose down -v`로 지워진다.
- 이미지 태그를 패치 버전까지 고정할지. 지금은 `mysql:8.4`라서 8.4 계열의 최신 패치를 받는다.
