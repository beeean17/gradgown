# 정적 계열

- 상태: 제안 (2026-11-14). 도구는 후보이고 확정하지 않았다
- 관련: [테스트 개요](./README.md), [dynamic.md](./dynamic.md), [tech-stack.md](../decisions/tech-stack.md), [db-privileges.md](../decisions/db-privileges.md)

코드를 실행하지 않고 하는 검사다. DB 없이 돌고 빨리 끝나야 한다. 커밋하기 전에 매번 돌리는 것을 기준으로 삼는다.

## 서버 (Java)

| 검사 | 무엇을 잡나 | 도구 후보 |
|---|---|---|
| 컴파일 | 타입 오류. 컴파일러 경고도 오류로 취급한다 | `javac -Xlint:all -Werror` |
| 형식 | 들여쓰기, import 순서 같은 형식 차이 | Spotless |
| 구조 규칙 | 아래 "구조 규칙" | ArchUnit |

컴파일 검사는 모든 모듈에 적용된다(루트 `build.gradle.kts`). 형식과 구조 규칙은 아직 넣지 않았다. 지금 돌릴 수 있는 정적 검사는 `./gradlew compileJava compileTestJava`뿐이다.

구조 규칙 가운데 둘은 도구 없이 모듈 경계로 지켜진다. `core`는 JDK 말고는 아무것도 의존하지 않아서 도메인 규칙이 웹 프레임워크나 DB에 기댈 수 없고, 마스터 계정의 설정은 `admin-server`에만 있어서 학생용 서버가 참조할 수 없다. "SQL은 저장소 계층에만"과 "저장소 메서드는 사용자 ID를 받는다"는 지금 코드가 지키고 있지만 검사하는 도구는 없다.

정적 분석 도구(SpotBugs, Error Prone 등)는 더 넣지 않는다. 과제 규모에서는 컴파일러 경고와 구조 규칙으로 충분하다고 본다.

### 구조 규칙

이 프로젝트에서 구조로 지킬 가치가 있는 규칙이다. 코드가 생기면 실제 패키지 이름으로 다시 적는다.

| 규칙 | 이유 |
|---|---|
| SQL은 저장소 계층에만 둔다. 컨트롤러와 서비스는 DB 접근 객체를 직접 쓰지 않는다 | 보고서에 실을 "DB와 상호작용하는 코드"가 한곳에 모인다. 쿼리를 찾고 검토하기 쉽다 |
| 학생용 서버에서 예약·신청을 읽거나 고치는 저장소 메서드는 모두 사용자 ID를 인자로 받는다 | 사용자 간 경계는 DB가 지켜 주지 않는다([db-privileges.md](../decisions/db-privileges.md)). 사용자 조건 없이 조회하는 메서드를 만들 수 없게 한다 |
| 학생용 서버는 관리자·마스터 DB 계정의 설정을 참조하지 않는다 | 서버를 나눈 이유가 접속 계정의 분리다([admin-server-split.md](../decisions/admin-server-split.md)). 계정 설정을 공용 모듈 `core`에 두지 않고 서버 모듈마다 두기로 해서(2026-11-18) 모듈 경계가 이것을 지킨다 |
| 도메인 규칙 코드는 웹 프레임워크와 DB에 의존하지 않는다 | 기간 판정 같은 규칙을 DB 없이 테스트할 수 있다 |

ArchUnit은 테스트로 실행되지만 컴파일된 코드의 구조만 읽는다. DB가 필요 없으므로 정적 계열에 둔다.

## SQL

| 검사 | 무엇을 잡나 | 도구 후보 |
|---|---|---|
| 형식과 문법 | DDL, `GRANT`, 시드 스크립트의 형식 차이와 뚜렷한 문법 오류 | SQLFluff (MySQL 방언) |
| 권한 표 대조 | `GRANT` 스크립트가 [db-privileges.md](../decisions/db-privileges.md)의 표와 같은지 | 사람이 검토 |

SQL은 정적으로 확인할 수 있는 것이 적다. 제약과 권한이 실제로 동작하는지는 MySQL에서 실행해 봐야 안다([dynamic.md](./dynamic.md)).

## 웹 (TypeScript)

원본에 이미 있는 검사를 그대로 쓴다. 학생 웹과 관리자 앱에서 돌아간다(2026-11-18). 관리자 앱은 `admin-web`에서 `npx tsc --noEmit`, `npx oxlint src`이고, 잔존 검사는 같다.

```sh
cd web
npx tsc -b                                        # 타입
npx oxlint                                        # 린트
! grep -rnE "from ['\"]firebase|firebase/" src   # Firebase 잔존 검사. 아무것도 나오지 않아야 한다
```

| 검사 | 무엇을 잡나 | 도구 |
|---|---|---|
| 타입 | 타입 오류. 서버 응답 타입을 바꿨을 때 영향받는 화면 | `tsc` (원본의 빌드에 포함) |
| 린트 | 흔한 실수 | `oxlint` (원본 사용 중) |
| Firebase 잔존 검사 | `firebase/*` import가 소스에 남아 있는지 | 린트 규칙 또는 검색 스크립트 |

**Firebase 잔존 검사**는 이 프로젝트에만 있는 검사다. 데이터 계층을 다 바꿨다면 웹 소스에 Firebase import가 하나도 없어야 한다. 이전이 끝났는지를 기계적으로 확인하는 기준이 된다.

## 웹과 서버 사이

| 검사 | 무엇을 잡나 | 방법 |
|---|---|---|
| 응답 타입 일치 | 서버가 주는 JSON과 웹의 화면 타입(`shared/types/index.ts`)이 어긋남 | 미정 |

방법은 둘이다.

- 서버에서 API 명세(OpenAPI)를 뽑아 웹 타입을 생성하고 차이를 비교한다. grad42의 PostgreSQL 이전 브랜치가 이 방식이다. 설정할 것이 많다.
- 정적으로는 검사하지 않고, 동적 계열의 계약 테스트가 응답의 필드를 확인한다([dynamic.md](./dynamic.md)).

과제 규모에서는 뒤쪽을 제안한다.

## 실행

- 정적 검사 전체를 명령 하나로 돌릴 수 있게 한다. 서버, 웹, SQL을 차례로 부른다.
- 실패하면 커밋하지 않는다.
- 같은 명령을 GitHub Actions의 정적 작업이 돌린다([ci.md](../decisions/ci.md)).

## 미정

- 서버 도구의 확정. 특히 Spotless의 형식 규칙과 ArchUnit을 쓸지.
- SQLFluff를 쓸지. SQL 파일이 몇 개뿐이면 빼도 된다.
- 응답 타입 일치를 어느 방법으로 검사할지.
- 관리자 앱을 가져오는 범위([API 계약](../contracts/web-api.md)). 범위에 따라 웹 쪽 검사 대상이 달라진다.
