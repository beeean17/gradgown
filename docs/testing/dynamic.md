## 1·2층의 구현 (2026-11-16)

**JUnit과 Testcontainers로 쓴다(확정).** 코드는 `db/src/test/java/gradgown/db/`에 있다. 2026-11-18에 로컬에서 167개가 모두 통과했다(스키마 42, 권한 124, 구성 1. MySQL 8.4.13). CI에서는 아직 돌리지 않았다. 워크플로가 없다.

| 파일 | 내용 |
|---|---|
| `MySqlTestDatabase` (`db/src/testFixtures/`. 서버 테스트도 쓴다) | 테스트 실행 한 번에 임시 MySQL 컨테이너 하나를 띄운다. `db/conf`와 `db/init`을 개발용 컨테이너와 같은 방식으로 적용하고, 이어서 테스트용 행(`src/test/resources/test-fixture.sql`)을 넣는다 |
| `SchemaConstraintTest` | 1층. 마스터 계정으로 접속한다 |
| `PrivilegeTest` | 2층. 검사하려는 계정으로 접속한다 |
| `ComposeFileTest` | `compose.yaml`의 이미지 태그가 테스트와 같은지 본다. MySQL이 필요 없다 |

- **DB 상태 되돌리기.** 테스트마다 트랜잭션을 열고 끝나면 되돌린다. 다른 접속이 봐야 해서 커밋해야 하는 테스트(공지 뷰)는 넣은 행을 직접 지운다. 이 방법은 1·2층에만 해당한다.
- **시드 데이터와의 관계.** 테스트는 시드 데이터에 기대지 않는다. 테스트용 행은 ID 9001 이상, 2037년, `.example` 도메인을 써서 시드 데이터와 겹치지 않는다.
- **거부의 판정.** MySQL의 오류 번호로 판정한다. 메시지 문구에 기대지 않는다.

| 거부의 종류 | 오류 번호 |
|---|---|
| PK·UNIQUE 중복 | 1062 |
| `CHECK` 위반 | 3819 |
| FK가 가리키는 행이 없음 | 1452 |
| FK가 가리키고 있는 행을 삭제 | 1451 |
| `ENUM`에 없는 값 | 1265 |
| 테이블 권한 없음 | 1142 |
| 컬럼 권한 없음 | 1143 |

- **권한 거부를 보이는 방법.** MySQL은 문장을 실행하기 전에 권한을 검사하므로, 어떤 행도 바꾸지 않는 문장(`WHERE 1 = 0`)으로 거부를 확인한다. 허용되는 쓰기는 실제로 실행하고 되돌린다.

```sh
./gradlew :db:test    # Docker가 켜져 있어야 한다
```

## 3~6층의 구현 (2026-11-18)

서버 두 개와 함께 썼다. 도구는 1·2층과 같다(JUnit, Testcontainers). 아래 방법은 확인받지 않은 제안이고, 그대로 구현해 통과하는 상태다.

| 층 | 어디 | 방법 |
|---|---|---|
| 3. 단위 | `core/src/test/` | DB도 서버도 없이 규칙 코드만 부른다 |
| 4. 통합 | `student-server/src/test/`의 `ReservationCommandTest`, `MentoringCommandTest`, `UserBoundaryTest`. `admin-server/src/test/`의 `AdminReadTest`, `AdminRoleTest` | 서버를 임의 포트에 실제로 띄우고 HTTP로 요청한다. 브라우저 하나가 쿠키 저장소 하나다 |
| 5. 동시성 | `student-server/src/test/`의 `ConcurrencyTest` | 로그인한 브라우저 8개가 같은 순간에 요청한다 |
| 6. 계약 | `student-server/src/test/`의 `ContractTest` | 응답의 필드 이름 집합과 값의 형식을 화면 타입과 대조한다 |

- **DB 상태 되돌리기.** 테스트마다 시작 전에 모든 테이블을 비우고 시드 데이터(`db/init/04-seed.sql`)를 다시 넣는다(`MySqlTestDatabase.resetToSeed()`). 서버가 커밋한 것을 되돌려야 해서 1·2층의 트랜잭션 되돌리기를 쓸 수 없다.
- **시각.** 학생용 서버의 테스트는 시계를 2026-12-01 10:00(서울)으로 고정한다. 시드의 신청 기간 안이다. 기간 밖을 볼 때는 테스트가 시계를 옮긴다. 서버는 현재 시각을 DB가 아니라 주입받은 `Clock`에서 읽는다.
- **시간대.** 테스트 JVM은 UTC로 돈다(`build.gradle.kts`). CI와 같은 조건이고, JVM의 시간대에 기대는 코드가 있으면 9시간 어긋난 값으로 드러난다.
- **개수.** 2026-11-18에 로컬에서 257개가 모두 통과했다: 스키마·권한 167, 단위 19, 학생용 서버 48, 관리자용 서버 23.
- **DB 밖에서 확인.** 서버의 응답만 믿지 않고, 테스트가 마스터 계정으로 테이블을 직접 읽어 결과를 확인한다(거부된 요청 뒤에 행이 그대로인지 등).

```sh
./gradlew test    # 전체. Docker가 켜져 있어야 한다
```

### 테스트를 쓴 사람이 아닌 쪽의 검증 (2026-11-18)

자동 테스트는 서버를 쓴 쪽이 예상한 경우만 본다. 그래서 서버를 쓰지 않은 별도의 검증을 세 번 돌렸다(모두 AI 에이전트이고, 구현의 설명 없이 문서와 코드만 받았다).

| 검증 | 방법 | 결과 |
|---|---|---|
| 코드 읽기 | 학생용 서버와 `core`의 모든 SQL과 흐름을 스키마·권한·계약과 대조 | 사용자 간 경계, 권한에 걸리는 SQL, 명령이 두 번 실행되는 순서는 찾지 못했다. 결함 3건 |
| 바깥에서 두드리기 (학생용) | 학생용 서버를 실제로 띄우고 `curl`로 계약이 예상하지 않은 요청을 보냄. DB를 직접 읽어 결과 대조 | 다른 학생의 데이터에 닿는 경로는 없었다. 결함 6건(3건은 위와 겹침) |
| 바깥에서 두드리기 (관리자용) | 두 서버를 띄우고 관리자·마스터·비로그인 요청을 섞어 보냄. MySQL의 일반 로그로 문장마다 어느 DB 계정이 실행했는지 확인. 행 수백 건을 넣고 목록을 SQL과 대조 | 24개 병렬로 섞어 보낸 3,150건에서 관리자의 문장은 모두 조회 계정으로, 마스터의 문장은 모두 마스터 계정으로 실행됐다. 관리자의 쓰기는 한 건도 반영되지 않았다. 결함 6건. 위에서 고친 학생용 7건은 모두 고쳐진 것으로 확인 |

찾은 결함은 모두 고치고, 각각을 다시 잡을 테스트를 더했다.

| 결함 | 자동 테스트가 놓친 이유 |
|---|---|
| 변경이 커밋된 뒤 응답만 끊기면 감사 로그가 `failed`로 덮여서, 같은 요청을 다시 보냈을 때 재요청으로 처리되지 않는다 | 연결이 끊기는 순간을 테스트가 만들지 않는다 |
| 연도가 터무니없는 시각(`9999-…`)을 보내면 500이 난다 | 형식이 틀린 값만 넣어 봤고, 형식은 맞지만 범위를 벗어난 값을 넣지 않았다 |
| `2.9`나 `"1"`이 정수로 바뀌어 저장된다 | 테스트가 항상 정수를 보냈다. JSON 라이브러리가 값을 바꿔 준다는 것을 몰랐다 |
| 학과를 빼고 변경하면 저장된 학과가 지워진다 | 테스트가 항상 모든 필드를 보냈다 |
| `Accept`가 JSON을 허용하지 않으면 모든 오류가 빈 500이 된다 | 테스트 클라이언트가 `Accept`를 보내지 않았다 |
| 없는 경로, 틀린 메서드, JSON이 아닌 본문의 오류가 계약의 형식이 아니다 | 테스트 클라이언트가 항상 올바른 경로와 형식으로 보냈다 |
| CORS 사전 요청이 로그인이 필요한 경로에서 500이 난다 | 브라우저가 아니라서 사전 요청을 보내지 않았다 |
| 행사 목록을 10개 이상 동시에 읽으면 연결 풀이 바닥나 그 DB 계정을 쓰는 모든 요청이 30초씩 멈춘다. 행을 읽는 도중에 다른 쿼리를 실행해서 요청 하나가 연결 둘을 잡았다 | 관리자용 서버의 테스트는 요청을 하나씩 보냈다 |
| `Accept`가 JSON을 허용하지 않으면, 실행된 명령에도 400으로 답한다 | 위의 오류 응답을 고칠 때 성공 응답은 보지 않았다 |
| UTF-8이 아닌 쿼리 문자열, 만들어질 수 없는 커서 값에 500이 난다 | 테스트가 올바른 값이나 형식이 틀린 값만 보냈다 |
| 접수 열기·닫기가 `"false"`나 `0`을 불리언으로 바꿔 받는다 | 학생용 서버에서 같은 문제를 고치고 관리자용 서버에는 적용하지 않았다 |

공통점은 **테스트 클라이언트가 서버를 쓴 사람의 가정을 그대로 가지고 있었다**는 것이다. 스키마와 권한이 지키는 규칙(중복 예약, 선택지, 역할 간 경계)에서는 결함이 나오지 않았고, 나온 것은 모두 서버 코드가 입력을 받아들이는 경계와 자원을 다루는 방식에서였다.

### 알고도 고치지 않은 것

검증에서 나왔지만 과제의 범위 밖이라고 보고 그대로 둔 것이다. 보고서의 한계에 적을 수 있다.

| 항목 | 내용 |
|---|---|
| 접수를 닫는 순간에 진행 중이던 명령 | 학생용 서버는 회차 행을 잠그지 않고 읽는다. 접수가 열려 있는 것을 확인한 직후에 마스터가 닫으면, 그 명령은 닫힌 뒤에 커밋될 수 있다. 원본은 설정을 같은 트랜잭션에서 읽어서 이 틈이 없었다 |
| 문자열 비교가 느슨하다 | 기본 정렬(`utf8mb4_0900_ai_ci`)은 대소문자, 악센트, 전각·반각을 구분하지 않는다. `２０２７-０２`가 회차 `2027-02`로 통하고, 전각 문자로 쓴 이메일로 로그인된다 |
| 등급은 로그인할 때 정해진다 | 세션에 든 등급을 쓴다. 로그인한 뒤에 `users.role`을 바꿔도 그 세션에는 반영되지 않는다 |
| 서버 코드에 닿기 전의 오류 | 주소 자체가 잘못된 요청은 Tomcat이 HTML 400으로 답한다. `TRACE`와 `/error`도 계약의 오류 형식이 아니다 |
| 멈춘 `operationId` | 2분이 지나면 실패로 답하지만 감사 로그의 행은 `received`로 남는다 |
| 감사 로그의 시각 | 응답은 초 단위다. 정렬과 커서는 밀리초를 쓴다 |

## 1. 스키마 테스트

빈 DB에 DDL을 적용한 뒤, [data-model.md](../decisions/data-model.md)의 "코드에서 DB 제약으로 옮기는 규칙"을 하나씩 확인한다. 규칙마다 **거부되는 경우와 허용되는 경우**를 둘 다 본다.

| 규칙 | 거부되어야 하는 것 | 허용되어야 하는 것 |
|---|---|---|
| 적용 | — | 빈 DB에 DDL 전체가 오류 없이 적용된다 |
| 회차당 유효 예약 하나 (RES-22) | 같은 사용자·회차에 `reserved` 두 건 | 취소한 뒤 다시 신청. 다른 회차에 신청 |
| 행사당 유효 신청 하나 (MNT-22) | 같은 사용자·행사에 `reserved` 두 건 | 취소한 뒤 다시 신청 |
| 슬롯은 같은 회차의 것 | 다른 회차의 슬롯을 참조하는 예약 | 같은 회차의 슬롯 |
| 선택지는 그 행사의 것 | 다른 행사의 선택지 번호 | 같은 행사의 선택지 |
| 두 차시에 같은 선택지 불가 (MNT-25) | 1차시와 2차시가 같은 번호 | 서로 다른 번호 |
| 둘 다 "선택 안함" 불가 (MNT-25) | 두 차시 모두 `NULL` | 한 차시만 `NULL` |
| 대리 수령 정보 | 대리 수령인데 이름이나 전화가 없음 | 대리 수령이 아니고 둘 다 비어 있음 |
| 값의 범위 | 학년 5, 선택지 번호 8, 사이즈 `xl` | 범위 안의 값 |
| 슬롯 중복 | 같은 회차에 같은 시작 시각의 슬롯 둘 | 다른 시작 시각 |
| 요청 중복 (RES-25) | 같은 `operation_id` 두 번 | 다른 `operation_id` |
| 참조 무결성 | 예약이 참조하는 슬롯이나 사용자를 삭제 | 참조가 없는 행 삭제 |

## 2. 권한 테스트

계정별로 접속해서 [db-privileges.md](../decisions/db-privileges.md)의 권한 표를 칸마다 확인한다.

| 계정 | 거부되어야 하는 것 | 허용되어야 하는 것 |
|---|---|---|
| 학생 | 예약·신청 `DELETE`. 회차·슬롯·선택지 쓰기. `announcements`와 `faqs` 테이블 직접 조회. `users`의 마지막 로그인 시각 외 컬럼 `UPDATE`. 예약·신청·감사 로그의 주인, 회차·행사, 생성·수정 시각 컬럼 `UPDATE` | 예약·신청 `SELECT`, `INSERT`, `UPDATE`. 공지 뷰 조회. `audit_logs` 기록 |
| 관리자 | 모든 테이블의 `INSERT`, `UPDATE`, `DELETE` | 모든 테이블 `SELECT` |
| 마스터 | 테이블 구조 변경 | 모든 테이블 읽기와 쓰기 |

뷰는 따로 확인한다. 숨김 공지를 넣은 뒤 학생 계정으로 뷰를 읽으면 그 공지가 나오지 않아야 한다.

## 3. 단위 테스트

DB와 서버 없이 도메인 규칙만 검사한다. 스키마로 표현하지 못해 서버 코드에 남은 규칙이 대상이다.

| 규칙 | 확인할 것 |
|---|---|
| 신청 가능 판정 (RES-21) | 접수가 닫혀 있으면 기간 안이어도 불가. 기간의 시작·끝 시각 정각은 불가(양끝 제외). 변경·취소는 수정 기간과 신청 기간 둘 다에서 가능 |
| St:talk 기간 판정 (MNT-21) | 신청·변경·취소가 같은 기간을 쓴다 |
| 반납은 대여 이후 (RES-13) | 같은 시각은 허용, 앞선 시각은 거부 |
| 입력 형식 | 전화번호 형식, 학번(St:talk은 숫자 8자리), 이름 길이, 사이즈 대소문자 처리 |
| 시각 변환 | 서울 오프셋 ISO 문자열. 자정 근처 슬롯의 날짜가 밀리지 않는다 |
| "선택 안함" 변환 | API의 `0`과 DB의 `NULL`이 서로 바뀐다 |

## 4. 통합 테스트

서버를 실제 MySQL에 붙여서 요청을 보낸다. 테스트마다 정해진 시드 데이터에서 시작한다.

### 명령 흐름

| 상황 | 기대 결과 |
|---|---|
| 신청 → 변경 → 취소 → 다시 신청 | 모두 성공. 취소한 건은 남고 새 건이 생긴다 |
| 같은 `operationId`로 다시 요청 (RES-25) | `replayed: true`. 행은 하나뿐이다 |
| 실패한 `operationId`를 다시 사용 (RES-26) | 거부 |
| 다른 사용자가 쓴 `operationId` | `permission-denied` |
| 이미 유효한 신청이 있는데 또 신청 | `already-exists` |
| 오래된 `version`으로 변경 (RES-24) | `aborted` |
| 접수가 닫혔거나 기간 밖 | `failed-precondition` |
| 비활성 슬롯 선택 (RES-14) | `failed-precondition` |
| 지난 회차의 예약 변경 (RES-23) | `failed-precondition` |
| 취소된 건을 변경 | `failed-precondition` |
| 모든 명령 | `audit_logs`에 결과가 남는다. 이름·학번·전화는 남지 않는다 (RES-32) |

### 사용자 간 경계

DB가 지켜 주지 않는 부분이라 반드시 둔다.

| 상황 | 기대 결과 |
|---|---|
| 학생 A가 학생 B의 예약 ID로 변경·취소 | 거부. B의 예약은 그대로다 |
| 학생 A의 내 예약 목록 | B의 예약이 섞이지 않는다 |
| 로그인하지 않은 요청 | 401 |
| 학생 계정으로 관리자용 서버에 로그인 | 거부 |

### 관리자 조회

| 상황 | 기대 결과 |
|---|---|
| 명단 검색 (이름, 학번, 전화) | 첫 페이지 밖의 일치 항목도 찾는다 |
| 상태·회차 필터와 페이지 넘김 | 빠지거나 겹치는 행이 없다 |
| St:talk 신청 인원 집계 | 선택지 × 차시 인원이 시드 데이터에서 계산한 값과 같다. 취소 건은 세지 않는다 |
| 공지 목록 | 학생 API에는 숨김 공지가 없고, 관리자 API에는 있다 |

### 관리자 쓰기

접수 열기·닫기는 관리자 쪽의 유일한 쓰기다([scope.md](../decisions/scope.md)). 등급에 따라 DB 계정이 달라지는 것을 여기서 본다([admin-server-split.md](../decisions/admin-server-split.md)).

| 상황 | 기대 결과 |
|---|---|
| 마스터가 회차의 접수를 닫음 | 성공. 학생 API의 회차 응답이 닫힘으로 바뀌고, 이후 신청은 `failed-precondition` |
| 관리자가 접수를 바꾸려 함 | `permission-denied`. MySQL의 오류 1142에서 온 것이다. 값은 그대로다 |
| 선택지 이름이 비어 있는 행사의 접수를 엶 (MNT-51) | `failed-precondition` |

## 5. 동시성 테스트

같은 요청을 동시에 보내서, 스키마가 정합성을 지키는지 본다.

| 상황 | 기대 결과 |
|---|---|
| 한 사용자가 같은 회차에 신청 두 건을 동시에 보냄 | 하나만 성공한다. `reserved`는 한 건이다 |
| 같은 예약을 같은 `version`으로 동시에 변경 | 하나만 성공하고 하나는 `aborted` |
| 같은 `operationId`를 동시에 보냄 | 한 번만 처리된다 |

Firebase 버전은 이것을 함수 안의 트랜잭션 조회로 막았다. 이 프로젝트는 UNIQUE 제약과 PK가 막는다는 것을 보이는 테스트다.

## 6. 계약 테스트

응답이 [API 계약](../contracts/web-api.md)과 같은 모양인지 본다. 웹의 화면 타입과 서버 응답이 어긋나는 것을 여기서 잡는다([static.md](./static.md)의 "웹과 서버 사이").

- 필드 이름과 타입이 화면 타입(`ReservationPeriod`, `Reservation`, `MentoringEvent`, `MentoringRegistration`, `Announcement`)과 같다.
- 시각은 서울 오프셋 ISO 문자열이다.
- ID와 `version`은 문자열이다.
- 오류 본문은 `{ code, message, operationId }`이고, `code`와 HTTP 상태가 계약의 표와 같다.

## 7. 브라우저 테스트

화면에서 흐름이 끝까지 되는지 본다. 보고서에 실을 화면도 여기서 얻는다.

| 시나리오 | 내용 |
|---|---|
| 학위복 예약 | 테스트 계정 로그인 → 4단계 신청 → 내 예약에서 변경 → 취소 → 다시 신청 |
| St:talk 신청 | 로그인 → 차시 선택 → 내 신청에서 변경 → 취소 |
| 기간 밖 | 접수를 닫으면 신청 버튼이 사라지고 안내가 보인다 |
| 관리자 조회 | 관리자 계정 로그인 → 명단 검색 → St:talk 신청 인원 표 |

처음에는 손으로 확인하고 체크리스트로 남긴다. 자동화(Playwright 등)는 미정이다. 원본의 관리자 앱에는 Playwright 스크립트가 있어 참고할 수 있다.

### 확인한 결과 (2026-11-18)

두 웹을 실제 서버와 MySQL에 붙여 놓고, 설치된 Chrome을 헤드리스로 띄워 DevTools 프로토콜로 조작했다(AI 에이전트가 수행). 마우스·터치·키보드 입력을 실제로 보내고, 화면의 글자와 `/api` 요청 기록으로 판정했다. 스크립트는 저장소에 두지 않았고, 화면 갈무리는 로컬의 `artifacts/browser-check/`에 있다(커밋하지 않는다).

| 시나리오 | 데스크톱 (1280×900) | 모바일 (390×844) |
|---|---|---|
| 비로그인: 홈의 일정, St:talk 안내, 공지 목록과 상세 | 통과 | 통과 |
| 로그인 화면·로그인 모달로 로그인, 계정 메뉴, 로그아웃 | 통과 | 고친 뒤 통과 |
| 학위복 예약: 4단계 신청 → 내 신청 → 시간·사이즈·대리 수령 변경 → 취소 → 다시 신청 | 통과 | 통과 |
| St:talk 신청: 신청 → 변경("선택 안함" 포함) → 취소 → 다시 신청 | 통과 | 통과 |
| 기존 데이터가 있는 학생의 내 신청 | 통과 | 통과 |
| 두 탭에서 두 번 신청 (`already-exists`) | 통과 | 통과 |
| 두 탭에서 같은 예약 변경 (`aborted`, 다시 읽은 뒤 저장 성공) | 통과 | 통과 |
| 접수를 닫으면 버튼이 사라지고 안내가 보인다 | 고친 뒤 통과 | 고친 뒤 통과 |
| 명령 중에 서버에 닿지 못함 (같은 `operationId`로 재시도하면 `replayed: true`, 행은 하나) | 고친 뒤 통과 | 고친 뒤 통과 |
| 조회 중에 서버에 닿지 못함, 다시 시도, 저절로 회복 | 고친 뒤 통과 | 고친 뒤 통과 |
| 관리자 조회: 관리자 로그인 → 명단 검색 → St:talk 신청 인원 표 → 감사 로그 | 통과 | 하지 않음 |
| 마스터: 접수 설정에 스위치가 보인다. 관리자에게는 보이지 않는다 | 통과 | 하지 않음 |

접수를 닫은 뒤 홈 화면에 "접수 닫힘"이 뜨기까지 23~27초 걸렸다(30초마다 다시 읽는다). 탭이 다시 보이면 0.2초 안에 다시 읽는다.

브라우저에서 찾아 고친 것은 모두 웹 쪽이고, 서버나 계약을 바꿔야 하는 것은 없었다.

| 결함 | 원인 |
|---|---|
| 모바일의 로그인 안내가 "구글 계정"이라고 했다 | 이전하면서 문구 두 곳을 놓쳤다 |
| 접수가 닫힌 뒤에도 최대 30초 동안 입력 화면이 남았다 | 명령이 `failed-precondition`으로 거부돼도 회차를 다시 읽지 않았다 |
| 서버가 꺼진 채 연 화면이 새로 고칠 때까지 오류로 남았다 | 첫 조회가 실패하면 다시 읽기를 멈췄다 |
| "다시 시도"가 아무 일도 하지 않았다 | 실패한 것은 회차 조회인데 내 목록만 다시 읽었다 |
| 명령 직후 서버에 닿지 못하면 입력 화면이 조회 오류로 바뀌었다 | 명령 뒤의 다시 읽기가 실패한 것을 조회 오류로 보였다. 이미 값이 있으면 그대로 둬야 한다 |
| 두 번째 탭에서 다른 계정으로 로그인하면 첫 탭이 예전 이메일을 보인 채 새 계정의 예약을 보였다 | 두 탭이 세션 쿠키를 함께 쓴다. 다른 탭에서 계정이 바뀌면 새로 고치게 했다 |

여섯 가운데 넷은 **실시간 구독을 없애면서 생긴 것**이다. Firestore에서는 구독이 변경과 재연결을 알아서 전해 주었다. REST로 바꾸면 "언제 다시 읽을지"를 웹이 정해야 하고, 그 판단이 빠진 곳마다 화면이 낡은 값을 보였다.

#### 알고도 그대로 둔 것

- 약관 본문에 "로그인한 구글 계정의 이메일 주소"라는 문장이 남아 있다. 단체의 약관 문구는 그대로 두기로 했다([tech-stack.md](../decisions/tech-stack.md)).
- 비로그인 상태로 화면을 열 때마다 브라우저 콘솔에 `/api/me`의 401이 찍힌다. 화면에는 보이지 않는다.
- 서버가 꺼진 채로 화면을 열면 로그인한 사용자도 비로그인으로 보인다. 서버가 돌아온 뒤 새로 고치면 회복된다.
- 학생 웹의 내 신청은 서비스마다 카드 하나만 보인다(유효한 건, 없으면 가장 최근 취소 건). 지난 회차의 예약은 보이지 않는다. 원본의 설계다.
- 관리자 앱은 1024px 미만의 화면, 다크 모드, 지난 회차 조회를 화면으로 확인하지 않았다. 마스터의 스위치는 실제 서버에 대고 누르지 않았다(요청은 `curl`로, 화면 흐름은 미리보기로 확인).

## 측정은 테스트가 아니다

[evaluation.md](../decisions/evaluation.md)의 조회 구조 비교(읽는 행 수, 왕복 횟수, 실행 계획)는 통과와 실패가 없다. 테스트와 따로 `eval` 모듈로 두었고(`./gradlew :eval:measure`), 결과는 `eval/results/`에 있다([evaluation.md](../decisions/evaluation.md)).

## 실행

- 동적 계열은 MySQL이 필요하다. Docker 컨테이너로 띄우고, 테스트용 DB는 개발용 DB와 따로 둔다([mysql-docker.md](../decisions/mysql-docker.md)).
- 테스트마다 같은 상태에서 시작한다. 1·2층은 트랜잭션을 되돌린다. 서버를 띄우는 층은 테이블을 비우고 시드 데이터를 다시 넣는다.
- 권한 테스트는 계정 셋으로 각각 접속해야 하므로, 테스트 환경에 세 계정의 접속 정보가 모두 있어야 한다.
- 1, 2, 5층의 실행 결과는 보고서에 옮길 수 있는 형태로 남긴다.
- 1~6층은 GitHub Actions의 동적 작업에서도 돈다. MySQL은 CI 안에서 컨테이너로 띄운다([ci.md](../decisions/ci.md)).
