# 동적 계열

- 상태: 제안 (2026-11-14). 테스트 목록은 초안이고, 도구와 실행 방법은 정하지 않았다
- 관련: [테스트 개요](./README.md), [static.md](./static.md), [data-model.md](../decisions/data-model.md), [db-privileges.md](../decisions/db-privileges.md), [evaluation.md](../decisions/evaluation.md), [API 계약](../contracts/web-api.md)

실제로 실행해서 결과를 보는 검사다. 층이 일곱 개다.

| 층 | 대상 | 필요한 것 | 보고서 증빙 |
|---|---|---|---|
| 1. 스키마 | DDL과 제약 | MySQL | ● |
| 2. 권한 | 계정별 `GRANT`와 뷰 | MySQL | ● |
| 3. 단위 | 도메인 규칙 | 없음 | |
| 4. 통합 | 서버의 명령과 조회 | MySQL, 서버 | ● |
| 5. 동시성 | 동시에 들어온 요청 | MySQL, 서버 | ● |
| 6. 계약 | 응답 모양과 오류 형식 | MySQL, 서버 | |
| 7. 브라우저 | 화면에서의 전체 흐름 | 전부 | ● 화면 |

1, 2층은 서버 코드 없이 SQL만으로 돌릴 수 있다. DDL을 쓰자마자 만들 수 있으므로 가장 먼저 만든다.

## 1. 스키마 테스트

빈 DB에 DDL을 적용한 뒤, [data-model.md](../decisions/data-model.md)의 "코드에서 DB 제약으로 옮기는 규칙"을 하나씩 확인한다. 규칙마다 **거부되는 경우와 허용되는 경우**를 둘 다 본다.

| 규칙 | 거부되어야 하는 것 | 허용되어야 하는 것 |
|---|---|---|
| 적용 | — | 빈 DB에 DDL 전체가 오류 없이 적용된다 |
| 회차당 유효 예약 하나 (RES-22) | 같은 사용자·회차에 `reserved` 두 건 | 취소한 뒤 다시 신청. 다른 회차에 신청 |
| 행사당 유효 신청 하나 (MNT-22) | 같은 사용자·행사에 `reserved` 두 건 | 취소한 뒤 다시 신청 |
| 슬롯은 같은 회차의 것 | 다른 회차의 슬롯을 참조하는 예약 | 같은 회차의 슬롯 |
| 선택지는 그 행사의 것 | 다른 행사의 선택지 번호 | 같은 행사의 선택지 |
| 두 차시에 같은 선택지 불가 (MNT-25) | 1차시와 2차시가 같은 번호 | 서로 다른 번호 |
| 둘 다 "선택 안함" 불가 (MNT-25) | 두 차시 모두 `NULL` | 한 차시만 `NULL` |
| 대리 수령 정보 | 대리 수령인데 이름이나 전화가 없음 | 대리 수령이 아니고 둘 다 비어 있음 |
| 값의 범위 | 학년 5, 선택지 번호 8, 사이즈 `xl` | 범위 안의 값 |
| 슬롯 중복 | 같은 회차에 같은 시작 시각의 슬롯 둘 | 다른 시작 시각 |
| 요청 중복 (RES-25) | 같은 `operation_id` 두 번 | 다른 `operation_id` |
| 참조 무결성 | 예약이 참조하는 슬롯이나 사용자를 삭제 | 참조가 없는 행 삭제 |

## 2. 권한 테스트

계정별로 접속해서 [db-privileges.md](../decisions/db-privileges.md)의 권한 표를 칸마다 확인한다.

| 계정 | 거부되어야 하는 것 | 허용되어야 하는 것 |
|---|---|---|
| 학생 | 예약·신청 `DELETE`. 회차·슬롯·선택지 쓰기. `announcements`와 `faqs` 테이블 직접 조회. `users`의 마지막 로그인 시각 외 컬럼 `UPDATE` | 예약·신청 `SELECT`, `INSERT`, `UPDATE`. 공지 뷰 조회. `audit_logs` 기록 |
| 관리자 | 모든 테이블의 `INSERT`, `UPDATE`, `DELETE` | 모든 테이블 `SELECT` |
| 마스터 | 테이블 구조 변경 | 모든 테이블 읽기와 쓰기 |

뷰는 따로 확인한다. 숨김 공지를 넣은 뒤 학생 계정으로 뷰를 읽으면 그 공지가 나오지 않아야 한다.

## 3. 단위 테스트

DB와 서버 없이 도메인 규칙만 검사한다. 스키마로 표현하지 못해 서버 코드에 남은 규칙이 대상이다.

| 규칙 | 확인할 것 |
|---|---|
| 신청 가능 판정 (RES-21) | 접수가 닫혀 있으면 기간 안이어도 불가. 기간의 시작·끝 시각 정각은 불가(양끝 제외). 변경·취소는 수정 기간과 신청 기간 둘 다에서 가능 |
| St:talk 기간 판정 (MNT-21) | 신청·변경·취소가 같은 기간을 쓴다 |
| 반납은 대여 이후 (RES-13) | 같은 시각은 허용, 앞선 시각은 거부 |
| 입력 형식 | 전화번호 형식, 학번(St:talk은 숫자 8자리), 이름 길이, 사이즈 대소문자 처리 |
| 시각 변환 | 서울 오프셋 ISO 문자열. 자정 근처 슬롯의 날짜가 밀리지 않는다 |
| "선택 안함" 변환 | API의 `0`과 DB의 `NULL`이 서로 바뀐다 |

## 4. 통합 테스트

서버를 실제 MySQL에 붙여서 요청을 보낸다. 테스트마다 정해진 시드 데이터에서 시작한다.

### 명령 흐름

| 상황 | 기대 결과 |
|---|---|
| 신청 → 변경 → 취소 → 다시 신청 | 모두 성공. 취소한 건은 남고 새 건이 생긴다 |
| 같은 `operationId`로 다시 요청 (RES-25) | `replayed: true`. 행은 하나뿐이다 |
| 실패한 `operationId`를 다시 사용 (RES-26) | 거부 |
| 다른 사용자가 쓴 `operationId` | `permission-denied` |
| 이미 유효한 신청이 있는데 또 신청 | `already-exists` |
| 오래된 `version`으로 변경 (RES-24) | `aborted` |
| 접수가 닫혔거나 기간 밖 | `failed-precondition` |
| 비활성 슬롯 선택 (RES-14) | `failed-precondition` |
| 지난 회차의 예약 변경 (RES-23) | `failed-precondition` |
| 취소된 건을 변경 | `failed-precondition` |
| 모든 명령 | `audit_logs`에 결과가 남는다. 이름·학번·전화는 남지 않는다 (RES-32) |

### 사용자 간 경계

DB가 지켜 주지 않는 부분이라 반드시 둔다.

| 상황 | 기대 결과 |
|---|---|
| 학생 A가 학생 B의 예약 ID로 변경·취소 | 거부. B의 예약은 그대로다 |
| 학생 A의 내 예약 목록 | B의 예약이 섞이지 않는다 |
| 로그인하지 않은 요청 | 401 |
| 학생 계정으로 관리자용 서버에 로그인 | 거부 |

### 관리자 조회

| 상황 | 기대 결과 |
|---|---|
| 명단 검색 (이름, 학번, 전화) | 첫 페이지 밖의 일치 항목도 찾는다 |
| 상태·회차 필터와 페이지 넘김 | 빠지거나 겹치는 행이 없다 |
| St:talk 신청 인원 집계 | 선택지 × 차시 인원이 시드 데이터에서 계산한 값과 같다. 취소 건은 세지 않는다 |
| 공지 목록 | 학생 API에는 숨김 공지가 없고, 관리자 API에는 있다 |

## 5. 동시성 테스트

같은 요청을 동시에 보내서, 스키마가 정합성을 지키는지 본다.

| 상황 | 기대 결과 |
|---|---|
| 한 사용자가 같은 회차에 신청 두 건을 동시에 보냄 | 하나만 성공한다. `reserved`는 한 건이다 |
| 같은 예약을 같은 `version`으로 동시에 변경 | 하나만 성공하고 하나는 `aborted` |
| 같은 `operationId`를 동시에 보냄 | 한 번만 처리된다 |

Firebase 버전은 이것을 함수 안의 트랜잭션 조회로 막았다. 이 프로젝트는 UNIQUE 제약과 PK가 막는다는 것을 보이는 테스트다.

## 6. 계약 테스트

응답이 [API 계약](../contracts/web-api.md)과 같은 모양인지 본다. 웹의 화면 타입과 서버 응답이 어긋나는 것을 여기서 잡는다([static.md](./static.md)의 "웹과 서버 사이").

- 필드 이름과 타입이 화면 타입(`ReservationPeriod`, `Reservation`, `MentoringEvent`, `MentoringRegistration`, `Announcement`)과 같다.
- 시각은 서울 오프셋 ISO 문자열이다.
- ID와 `version`은 문자열이다.
- 오류 본문은 `{ code, message, operationId }`이고, `code`와 HTTP 상태가 계약의 표와 같다.

## 7. 브라우저 테스트

화면에서 흐름이 끝까지 되는지 본다. 보고서에 실을 화면도 여기서 얻는다.

| 시나리오 | 내용 |
|---|---|
| 학위복 예약 | 테스트 계정 로그인 → 4단계 신청 → 내 예약에서 변경 → 취소 → 다시 신청 |
| St:talk 신청 | 로그인 → 차시 선택 → 내 신청에서 변경 → 취소 |
| 기간 밖 | 접수를 닫으면 신청 버튼이 사라지고 안내가 보인다 |
| 관리자 조회 | 관리자 계정 로그인 → 명단 검색 → St:talk 신청 인원 표 |

처음에는 손으로 확인하고 체크리스트로 남긴다. 자동화(Playwright 등)는 미정이다. 원본의 관리자 앱에는 Playwright 스크립트가 있어 참고할 수 있다.

## 측정은 테스트가 아니다

[evaluation.md](../decisions/evaluation.md)의 조회 구조 비교(읽는 행 수, 왕복 횟수, 실행 계획)는 통과와 실패가 없다. 테스트와 따로 스크립트로 두고, 결과를 보고서에 싣는다. 합성 데이터의 규모가 정해져야 한다.

## 실행

- 동적 계열은 MySQL이 떠 있어야 돈다. 테스트용 DB는 개발용 DB와 따로 둔다.
- 테스트마다 같은 상태에서 시작한다. 방법(매번 스키마를 다시 만들기, 트랜잭션 되돌리기)은 미정이다.
- 권한 테스트는 계정 셋으로 각각 접속해야 하므로, 테스트 환경에 세 계정의 접속 정보가 모두 있어야 한다.
- 1, 2, 5층의 실행 결과는 보고서에 옮길 수 있는 형태로 남긴다.

## 미정

- 테스트용 MySQL을 띄우는 방법. Docker를 쓰면 Testcontainers로 테스트가 직접 띄울 수 있다.
- 1, 2층을 SQL 스크립트로 쓸지 서버의 테스트 코드(JUnit)로 쓸지.
- 테스트 사이에 DB 상태를 되돌리는 방법.
- 브라우저 테스트의 자동화 여부.
- 합성 데이터의 규모.
